# Mammogram images

How the prototype shows mammograms: the fake diagrams it uses today, how an appointment gets its images, and the real images being added. For the PACS viewer window itself, and the full manifest format, see [pacs-viewer.md](pacs-viewer.md).

## Two things called "mammogram data"

- **`appointment.mammogramData`** is the record of what was taken: which views, how many images each, repeats, the machine and room, when. Generated by `app/lib/generators/mammogram-generator.js`, or entered on the manual imaging page. It has no pictures.
- **An image set** is the pictures shown for those views. The appointment points at one by `mammogramData.selectedSetId`.

Keep these consistent: if `mammogramData` says RMLO was taken twice, the set should have two RMLO images.

## Diagram sets (what we use today)

Drawn diagrams, not real mammograms, so they are safe to commit and reuse.

- Folder: `app/assets/images/mammogram-diagrams/` - `set-XX/{rcc,lcc,rmlo,lmlo}.png`, an `image-library/` of single images (blurred, overexposed and so on), and `manifest.json`.
- The manifest tags each set `normal`, `abnormal`, `indeterminate` or `technical`, with per-breast status, flags (`hasImplants`, `hasRepeat`) and annotations. Sets can be composed from other sets and library images. Format: [pacs-viewer.md](pacs-viewer.md#manifest).
- Source and processed copies live in `reference/mammogram-diagrams-*`; `scripts/process-mammogram-sets.sh` and `scripts/process-mammogram-images.sh` prepare new ones.

### How an appointment gets a set

The appointment comes first and the set is chosen to fit it. `getImageSetForAppointment` in `app/lib/utils/mammogram-images.js`:

1. Uses `mammogramData.selectedSetId` if already stored, unless a tag or weights are forced.
2. Otherwise reads the appointment's context (`extractAppointmentContext`: symptoms and their side, implants, imperfect images, repeated views, breasts not imaged), filters to sets that match (implants, repeats), weights them by tag, and picks one with a random seeded by the appointment ID, so the same appointment gets the same set.

The fit is best effort. If filtering leaves no sets, it falls back to all of them, and matching the exact repeated views is only preferred. So a set can disagree with `mammogramData`.

The set ID is stored when appointments are generated (`appointment-generator.js`, `reading-generator.js`) and when images are recorded (`routes/appointments/imaging-automatic.js`, `imaging-manual.js`). Weights: `config.reading.mammogramTagWeights` and seed profiles.

`getImagesForAppointment` then returns the paths for the views present in `mammogramData`, the latest attempt for each view, and every attempt, which the viewer lets the reader flick between.

### Where images are shown

- Screening: the imaging pages (`appointments/images.html`, `images-automatic.html`) and image cards (`_includes/mammogram-image-cards.njk`, `mammogram-image-display.njk`).
- Reading: opinion thumbnails, annotation pages, compare, review, recall for assessment, existing reads, arbitration cards and the case page.
- The PACS viewer window, fed by `_includes/images/pacs-viewer-meta.njk`.

### Annotations

Annotations mark an abnormality on a breast, with a position on each view of that breast:

```json
{
  "side": "right",
  "positions": { "rmlo": { "x": 0.321, "y": 0.526 }, "rcc": { "x": 0.643, "y": 0.434 } },
  "abnormalityType": "Mass well-defined",
  "levelOfConcern": "5",
  "notes": "Cancer",
  "scale": 2.25
}
```

Positions are fractions of the image's width and height, so they hold at any image size as long as the image isn't cropped. Composite sets inherit annotations from the sets they borrow views from (`getResolvedAnnotations`).

The admin page `/admin/mammogram-sets` (`app/views/admin/mammogram-sets.html`) edits set metadata and places annotations, saving back to the diagrams `manifest.json`.

### Image source setting

Choose diagrams or real images on the settings page, under Image reading: "Mammogram images". It's stored per session as `data.settings.reading.mammogramImageSource`, `'diagrams'` or `'real'`. When no pack is present, the settings page says so instead of offering the choice. The default comes from `config.reading.mammogramImageSource`, which is `'diagrams'` unless the `MAMMOGRAM_IMAGE_SOURCE` environment variable says otherwise.

Nothing reads the setting directly: templates call `getMammogramImageSource()` in `mammogram-images.js`, which returns `'real'` only when the session's setting (or, outside a template, the config default) is `'real'`, a pack with usable cases is present, **and** the session has unlocked real images (see "Access code" below). Otherwise it returns `'diagrams'`.

Real images are for image reading only. `getMammogramImageSource('screening')` is always `'diagrams'`: screening pages, the generators and the imaging routes use it, so the set stored on an appointment (`mammogramData.selectedSetId`) is always a diagram set. Reading pages call `getMammogramImageSource()` and choose a real case at render time.

The route sweep and journey tests pin `MAMMOGRAM_IMAGE_SOURCE=diagrams`, so they run on diagrams whatever pack is present locally.

## Real images

We have a set of real, de-identified screening mammograms with screening history, to make usability testing more realistic. The prototype can show them in image reading from a local pack, with each case's earlier studies as priors in the PACS viewer, and seeded readers mark abnormalities where clinicians have annotated them. Hosting for deployed testing is still to come.

### Rules

- **Never commit real image data.** Not the images, nor anything derived from them: manifests, annotations, IDs, screenshots, test output. The repo holds code, schema and docs only.
- The prototype must work without the real images. Diagrams stay the default, and tests and CI run on diagrams.
- Raw DICOM files are processed offline into JPEGs and a manifest. The prototype never reads DICOM.
- **Don't put real images under `app/assets` or `public`.** The prototype kit serves those folders before it checks the password, so anything there is public on a deployed prototype. Real images must be served by a route that runs after the password check.
- A real set is one woman's complete study. Views are never mixed between women, unlike diagram composites.

### The source data

One folder per woman, holding:

- an image index (JSON) relating each **study** (one imaging visit) to its images, a study date, and usually an NBSS episode ID
- an NBSS extract (JSON) of her screening episodes: per breast, the screening opinion, each reader's opinion and recommended action, the final action; and for recalled episodes, assessment, biopsy and lesion details. Lesion locations are coded regions, not image coordinates.
- a folder of DICOM images per study.

Things that matter for using it:

- Some study folders aren't listed in the image index. Link them to an NBSS episode by date: image and NBSS dates are shifted by the same amount.
- Studies and episodes are not one-to-one. A recalled episode has a screening study and an assessment study. Older episodes predate digital imaging and have no images. The most recent study may have no NBSS episode, so no known outcome.
- Dates are shifted per woman. Gaps between her studies are kept, so only use dates relative to each other, and only the study date (other DICOM dates are shifted differently).
- A study can include more than one image of a view (a retake, or extra images to cover a large breast; the data doesn't say which), raw "for processing" images that must not be shown, assessment views (spot compression, ML, XCCL) and tomosynthesis-generated 2D images. Image headers say which.
- Several makes of machine, so image size and look vary. Real images are about 2500-3500 px tall and wider in proportion than the diagrams.
- Some images have text burned into the pixels (view labels, for example).
- Annotations don't exist. Abnormal cases need marking by hand, by someone clinically qualified (see "Annotating real cases" below).

### NBSS codes we rely on

From the NBSS reporting tables specification (DS0026). The PDF is kept with the project notes, outside the repo.

| Field                                                           | Codes                                                                                                                                                                                                              |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Screening `Opinion` per side                                    | `RN` normal, `RU` abnormal, `BA` clinical, `RO` unreported                                                                                                                                                         |
| Reader opinion (`FilmReaderNOpinion`)                           | `N` normal, `A` abnormal, `C` clinical, `T` technical recall                                                                                                                                                       |
| Reader and final action (`FilmReaderNRecAction`, `FinalAction`) | `RR` routine recall, `RC` review in clinic (recall to assessment), `FV` further X-ray views, `EC` early recall for clinic, `TR` repeat film (technical)                                                            |
| `FinalActionSource`                                             | `A` automatic (readers agreed), `D` human arbitration, `P` entered from paper                                                                                                                                      |
| `RepeatReason`                                                  | `R1A` / `R1B` inadequate positioning (radiographer / client), `R2` inadequate compression, `E1`-`E6` equipment or film faults                                                                                      |
| `LesionPosition`                                                | Side, then a cell on a front-on grid of the breast: columns `A` (axilla, outer) to `E` (inner), rows `1` (top) to `4` (bottom), `M` the nipple. `RB2` is right, outer, upper-middle. Not tied to a mammogram view. |
| Episode type in the extract                                     | `F` first call, `R` routine recall, `S` self referral, `G` GP referral, `H` higher risk, `CI` interval case, `N` non-routine recall, `X` other                                                                     |

Assessment opinions use the usual 1 (normal) to 5 (malignant) scales: `R` mammography, `U` ultrasound, `I` imaging overall, `P` clinical, `B` biopsy. The participant `Classification` comes from the image set's providers, not NBSS.

### What changes for real images

Real sets can't be bent to fit an appointment, so the direction reverses: choose the case, then shape the participant and appointment around it (age, history, repeats, implants). The case's earlier studies become **priors**, which the PACS viewer shows ([pacs-viewer.md](pacs-viewer.md#viewer-features)). Notes on options for storage, case assignment, priors and annotation are kept with the project's working notes, outside the repo.

### Surveying the full set

`scripts/real-images/survey.py` reads every participant's JSON and DICOM headers (not pixels) and reports what the set contains: outcomes, study types, duplicate views, machines, image sizes, and the NBSS code values in use. It needs Python 3.8+ and `pydicom`; usage is in the script's docstring. Its output contains pseudonymised IDs and outcomes, so it's treated like the data itself.

### Building a pack

`scripts/real-images/build-pack.py` turns the raw participant folders into a **pack**: `manifest.json`, a private `id-map.json` (our short aliases back to the original IDs) and JPEGs of every usable image, at display size (~1600 px tall) and full resolution. The prototype only ever reads a pack.

```sh
python3 -m venv pack-env
pack-env/bin/pip install -r scripts/real-images/requirements.txt
pack-env/bin/python scripts/real-images/build-pack.py /path/to/participant-folders --out /path/to/pack
```

- `--display-only` for a quick, small pack; `--skip-existing` to render only what's missing, so on an existing pack it rebuilds just the manifest in minutes (it still needs the raw data); `--limit N` for a trial run; `--check` to validate an existing pack's manifest; `--remove-duplicates` to take duplicate images out of a pack built before the builder dropped them (needs only the pack, not the raw data).
- It drops 'for processing' images, tomosynthesis slices, non-mammogram studies and images too small to be a full view, and mirrors images so a right breast's chest wall is on the right and a left's on the left. Images it can't orient are left as they are and flagged in `build.log`.
- The raw data sometimes holds the same image more than once, as separate files with their own IDs. Where images share a view and instance number and have identical pixels, it keeps the first and logs the rest in `build.log`; otherwise the copies would show as repeated views.
- A screening study within 60 days of a recalled one is treated as assessment, because the raw data rarely marks magnification or spot views. It isn't used as a case or a prior.
- Each screening study becomes a **case**, with only earlier screening studies as priors and its NBSS result (`normal`, `recalled-not-cancer`, `cancer`, `technical-repeat-requested`) for choosing the mix. Higher-risk participants are marked so they can be included or left out.
- It never overwrites the hand-made `annotations.json` and `curation.json` in the pack, and leaves out studies and images that `curation.json` excludes.
- The manifest is checked against the format at the end of every build, including a scan for original IDs or dates.

A pack is real image data: never commit it, and never put it under `app/assets` or `public`.

To share a pack, copy `manifest.json`, `images/`, and `annotations.json` and `curation.json` if they exist. Keep `id-map.json` and `build.log` with the raw data: both contain original IDs. `annotations.previous.json` and `annotation-backups/` are local safety copies from the annotator and don't need sharing.

### Showing a pack in the prototype

Put the pack at `real-images/` in the repo root (gitignored), or point `REAL_IMAGES_PATH` at it, start the prototype, and choose "Real images" on the settings page. To start with real images on, without the setting:

```sh
MAMMOGRAM_IMAGE_SOURCE=real REAL_IMAGES_PATH=/path/to/pack npm run start
```

Without a pack, the prototype shows diagrams.

- **Serving**: `GET /real-images/*` in `app/routes/real-images.js` serves files from the pack's `images/` folder. It's in the app's routes so it runs after the kit's password check (which the kit only turns on when `NODE_ENV=production`), and it returns 403 unless the session has unlocked real images. Paths outside `images/` and anything that isn't an image return 404. Responses are `Cache-Control: no-store`, so images aren't kept in the browser's cache on shared workstations; the browser downloads them again on each page. `getImageSource()` in `app/lib/real-images.js` decides where a file comes from; for remote storage it would return a redirect instead, without changing pages.
- **Loading**: `app/lib/real-images.js` reads `manifest.json`, `annotations.json` and `curation.json`, and turns each case into an image set like the diagram ones: tag, side statuses, `hasRepeat`, `hasImplants`, `paths` per view using the display JPEGs (an array ordered by instance when a view was taken more than once), `fullPaths` (the full-resolution JPEG for each display one, which the PACS viewer loads when zoomed in), `priors` (the case's earlier studies, newest first, each with its `paths`, `fullPaths` and `daysBefore` the case's study; excluded studies are left out), and annotations with image IDs mapped to view keys (`rmlo`, `rmlo-1`…). Cases tagged `unknown`, excluded studies and studies with no standard views are left out. It re-reads the files when they change.
- **Assignment** (`getRealAssignments` in `mammogram-images.js`): every imaged appointment in the seed data gets its own case, in order of appointment time. Candidates match its context (implants, repeats), its diagram set's tag (`indeterminate` becomes `abnormal`) and, where they can, which breasts are abnormal, so seeded reads mark the right breast. A real participant isn't used again until three quarters of the pack's participants have been used since, so a reading session, which takes appointments close together in time, doesn't show the same woman twice. Of those, it picks the case that best fits the participant (`getRealCaseFitCost`): age, number of priors, how long ago her last mammogram was, and routine or higher-risk screening. Deterministic for the same seed data and pack.
  - The exception is a tag with fewer real cases than appointments: real technical repeats are rare, so their women are reused, as far apart as possible.
  - Appointments not in the seed data are matched the same way, preferring cases and participants no seed appointment uses.
  - The seed data's reads count too (`getRealCaseReadsCost`): an appointment whose seeded readers recalled a breast prefers a case clinicians have marked on that breast, and one whose seeded readers disagreed prefers a case real readers found hard (they disagreed, or it was recalled and wasn't cancer). These only choose between cases that already fit, so with few annotated cases most recalls still land on unmarked ones.
- **Seeded reads**: while real images are on, a seeded "recall for assessment" read of a case clinicians have marked shows the clinicians' markers on each breast it calls abnormal, instead of its generated ones (`withRealImageReads` in `app/lib/utils/real-image-reads.js`). Each reader's markers are nudged slightly so two readers' don't sit exactly on top of each other. Opinions and which breasts are abnormal never change, so case status and arbitration are the same as with diagrams. It's applied per request by the middleware in `app/routes.js` and by `getEpisode`, and `recordEpisodeChange` puts back the generated markers before saving (finding seeded reads by reader and time, so a read finalised meanwhile is still caught), so nothing from the pack ends up in session data. Reads the user makes are never changed.
- **Participant age**: while real images are on, each seed participant's date of birth is moved by whole years so her age at the appointment is the real case's age. The middleware in `app/routes.js` that attaches the seed data applies it per request (`getRealImageDatesOfBirth`, `withRealImageDateOfBirth` in `participants.js`, also used by `getParticipant`), and it's never saved. A date of birth changed during the session is left alone. Her generated screening history isn't moved: cases are chosen to fit it, but prior dates in the viewer come from the pack.
- **Access code**: deployed, real images also need an access code, set in the `REAL_IMAGES_ACCESS_CODE` environment variable. Entering it unlocks real images for that session for `config.reading.realImagesAccessHours` (4 hours); until then pages show diagrams, with a banner linking to `/real-images-access` to enter it. Changing the code locks every session straight away. Codes are compared ignoring case and spaces, so use a few random words rather than a short code. A link can carry the code to unlock the session it opens, for example `/reading?_realImagesCode=the-code`; the route takes it out of the address straight away, but it can still end up in browser history and server logs, so change the code after a round of testing. With `NODE_ENV=production` and no code set, real images can't be unlocked at all; running locally without a code, they need none. The logic is in `app/lib/real-images-access.js`; the unlock is stored in `data._realImagesAccess`, which the kit never fills from a form or link because of its underscore.
- **Annotating real cases**: `/admin/real-cases` (`app/routes/admin-real-cases.js`, `app/views/admin/real-cases.html`, `app/assets/javascript/admin-real-cases.js`) is for clinicians to mark abnormalities on a pack's cases, on a local copy of the prototype. It isn't available when `NODE_ENV=production`. It lists cases worth marking: cancers, cases recalled and found normal at assessment or by biopsy, cases the real readers disagreed on, the last screen before an interval cancer, and technical repeats. A case can be in more than one group; filter by group and by status. Each case shows its 4 views, its NBSS details (a table of each reader's opinion per breast, assessment, lesion positions) as hints, and the participant's other studies. Only the cases in these groups need marking, not every study a participant has. Click a view to place a marker; a marker has a position on each view of the breast, abnormality types, level of concern, the eventual finding, notes and an optional size (`size`, its diameter as a fraction of the image's width, which the reading screens don't use yet). Give each case a status when finished: "Done", "Come back to this" or "Nothing visible". Changes save as you go to the pack's `annotations.json`, keeping the previous version in `annotations.previous.json` and a copy per day in `annotation-backups/`. The pack is in nodemon's ignore list (`app.js`), so saving doesn't restart the server.
- **Trying it without real data**: `node scripts/real-images/build-fake-pack.js /path/to/fake-pack` makes a small pack from the diagrams: priors, a repeated view, implants, annotations, a technical case and an `unknown` case.
